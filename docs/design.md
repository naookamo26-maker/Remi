# Remi(レミ) 設計書

改訂: 2026-11-21(実装に合わせて随時更新する。変更の経緯は CHANGELOG.md)

## 1. 目的と要件

Redmineのチケットを、チャットアプリのように監視・コメントできるWindows向けスタンドアロンアプリ(Python製)。サーバー負荷を抑えるため、リアルタイム性は多少犠牲にしてよい。

**アプリ名: Remi(レミ)**。Redmineの「Re」と「Reminder / Mini」を掛け合わせた響き。

| 項目 | 内容 |
| --- | --- |
| 言語・取得方法 | Python 3.14 / Redmine REST API(ポーリング) |
| パッケージ管理 | pip(`venv` + `requirements.txt`。開発用は `requirements-dev.txt` に分ける) |
| 対象OS | Windowsのみ |
| Redmine | 新しめのバージョン(5.x / 6.x 想定) |
| サーバー | 複数。ユーザーが登録・編集できる |
| 監視対象 | 担当・ウォッチ中のチケット。作成したチケットはプロジェクト単位で任意に追加(既定オフ) |
| 規模 | 1サーバーあたり監視対象が数百件になる場合を想定 |
| 今回の主機能 | チケットのコメント閲覧・投稿(Markdown / Textileのレンダリング、画像の表示を含む) |
| 将来の機能 | ステータス変更など。画面に拡張余地を残す |
| 未対応機能の扱い | 「ブラウザで開く」ボタンで逃がす |
| 常駐・通知 | トレイ常駐。通知は設定でON/OFF可能 |
| 画面 | HTML/CSSで作り、Windows標準のWebView2で表示する(§2)|
| 外観 | Windowsのダークモードに対応(§9) |
| 言語 | 多言語対応。最初は日本語と英語(§10) |
| バージョン | セマンティックバージョニング。ひとまずの完成までは `0.y.z`(§11) |

## 2. 全体アーキテクチャ

画面はHTML/CSS/JavaScriptで作り、Windows標準の **WebView2**(Edge = Chromium)で表示する。Pythonのバックエンドは、アプリ内だけで使うローカルHTTPサーバーとして画面にAPIを提供する。画面はAPIを通してローカルのSQLiteキャッシュだけを読み、Redmineへ直接アクセスしない。

| 層 | 役割 | 主な技術 |
| --- | --- | --- |
| 画面層 | ツリー・一覧・会話ビュー・ダイアログ | HTML / CSS / JavaScript(ビルド不要のESモジュール。外部CDNは使わない) |
| ウィンドウ層 | ウィンドウ、トレイ常駐、通知、自動起動 | pywebview(WebView2)、pystray、windows-toasts |
| ローカルAPI層 | 画面へのAPI(RPC)とイベント配信(SSE)、添付画像の配信 | 標準ライブラリの `http.server`(127.0.0.1のみ) |
| ストア層 | キャッシュ・既読状態・設定・下書き・画像キャッシュ | SQLite(WAL)+ ファイルキャッシュ |
| 同期エンジン層 | サーバーごとの独立ワーカーで差分ポーリング | `threading`(サーバーごとに1本) |
| APIクライアント層 | Redmine REST API呼び出し、認証 | requests + truststore |

方式の検討: Qtの部品(PySide6)+ `QTextBrowser` も検討したが、CSSのサブセットしか使えず、モックのデザイン(角丸、影、flex/grid、ダークモード)を再現できない。QtWebEngineはChromiumを同梱するため配布サイズが200MBを超える。対象がWindowsのみなので、OSに入っていてWindows Updateで更新されるWebView2を使う。

### 2.1 スレッドとDBアクセス

- SQLiteは **WALモード**。接続はスレッドごとに持つ(`sqlite3` の接続はスレッド間で共有しない)。
  終了したスレッドの接続は閉じる(ローカルHTTPサーバーは接続ごとにスレッドを作るため、閉じないと常駐中に増え続ける)
- 書き込みは短いトランザクションにまとめ、`busy_timeout` を設定する
- 同期ワーカーは書き込み後に、イベントバスへ「変更があった `(server_id, issue_id)` の一覧」だけを流す。画面はSSEでそれを受け取り、必要な部分だけAPIで読み直す
  (購読ごとのキューがあふれたら、古いイベントをすべて捨てて `resync` だけを残す。入れる側は購読ごとの鍵で1つずつにするので、
  複数のスレッドが同時にあふれさせても、`resync` は1つだけで、先頭に残る)。
  イベントを受け取り損ねても送信中のまま残らないよう、画面は `resync`(再接続を含む)を受け取ったら、送信中のチケットの結果を
  `getSendResult` で問い合わせ直す(バックエンドは、送信ごとの最後の結果を、画面が受け取るまで覚えておく)
- 同期スレッドが動いていない(APIキーを読めずに始められなかったなど)サーバーへの依頼(送信・ウォッチ・画像の取得)は受け付けない
  (受け付けても処理されず、結果が届かないため)

### 2.2 保存場所・秘密情報

- データ: `%LOCALAPPDATA%\Remi\`(`remi.db`、`cache\attachments\`、`logs\`)
- APIキー: Windows資格情報マネージャー(`keyring`)。DBには置かない

### 2.3 SSL証明書(Windows証明書ストア)

`pip-system-certs` は使わず、`truststore` を明示的に初期化する。([参考: Qiita](https://qiita.com/haravity/items/39bf7dcb869182839d71))

- アプリ起動時の最初、requests / urllib3 をimportする前に `truststore.inject_into_ssl()` を呼ぶ
- PyInstallerではruntime hook(`hook_truststore.py`)としても指定する
- ビルド時のエラーと、exe実行時のSSLエラーは別の原因として切り分ける
- 接続テストで証明書エラーを検出したら、原因をわかりやすく表示する

### 2.4 HTTPクライアント

- requestsを採用する(既存の類似アプリのコードを流用でき、少量のポーリングでは非同期の利点が小さく、スレッドで足りるため)
- サーバーごとに `requests.Session` を持ち、`X-Redmine-API-Key` ヘッダーを共通化する
- `timeout=(接続, 読み取り)` を必ず指定する
- プロキシ: 既定ではWindowsのプロキシ設定に従う(requestsがレジストリから読む)。PACには対応しないので、設定画面でサーバーごとにプロキシを手動指定することもできる
- **レート制御**: サーバーごとに同時に1リクエストだけ送る。
  - 「同時に1つ」は、リクエストの開始を直列にするという意味で、添付のダウンロードの本文の受信中は含めない(大きな添付が、画面操作の通信を止めないため)
  - **背景の同期**(差分・初回・コメントの遅延取得など)は、リクエストの間に最小間隔(0.5秒)を空ける。数百件の初回同期でもサーバーを叩きすぎない
  - **画面の操作**(チケットを開く・「詳細」や編集の選択肢・コメントの送信・項目の変更・ウォッチ・画像の取得・接続テスト)は、人が待っているので、
    最小間隔を空けず、背景の同期に先んじる(背景の同期は、画面の操作の通信が続いている間だけ譲る)。操作した分だけで、通信の量は増えない。
    一括で取得するもの(初回同期・バージョンのチケット)は、背景の同期として扱う
  - 同じ定義(トラッカー・ロール・カスタムフィールド・メンバーなど)を、画面が同時に求めても、取得は1回にまとめる

### 2.5 プロセス

- **同期スレッドの起動・停止**: 停止・起動・再試行は専用の鍵で直列にする。アプリの終了後は、再起動の要求や待っていた再試行でも起動しない

- **多重起動の防止**: 名前付きパイプ(`multiprocessing.connection`。Windowsでは `\\.\pipe\Remi-<ユーザーのハッシュ>`)で待ち受ける。2つ目を起動したときは、既存のプロセスに「表示」を依頼して終了する
- **終了の依頼**: `Remi.exe --quit` は、多重起動の防止と同じ名前付きパイプで、起動中のRemiに「終了」を依頼して終わる(起動していなければ何もしない)。
  ×ボタンではトレイに格納されるので、外から確実に終了させるために使う
- **配置先を SVN・Git で管理するとき**の更新用に、`packaging/Remi-update.bat` を配布物の `Remi.exe` と同じ場所に入れる。
  「終了(`--quit`。30秒待っても終わらなければ強制終了)→ `svn update` / `git pull --ff-only` → 再起動」を行う。
  SVN・Git は配置先で自動判定し、設定(`VCS`・`START_ARGS`・`WAIT_SECONDS`)は先頭で変えるか、環境変数で渡す。
  更新に失敗しても、いまのファイルで再起動し、エラーを知らせる(終了コード 2)
- **更新の確認**(`system/update_check.py`): 配布物で、`Remi.exe` のフォルダが SVN・Git で管理されているとき、起動して少ししてからと
  6時間ごとに、取り込んでいない更新があるかを確かめる。ファイルは書き換えない
  - Git: `git fetch` のあと、`git rev-list --count HEAD..@{u} -- .`(`Remi.exe` のフォルダに関係するコミットだけ)が1以上なら更新あり。
    SVN: `svn status --show-updates .` に、サーバーで新しくなったもの(9文字目が `*`)があれば更新あり
  - どちらで管理されているかは、`Remi-update.bat` と同じ順(Git → SVN)で、そのツールに問い合わせて決める。
    どちらでもない・コマンドがない・つながらない(認証を求められる)ときは、何もしない(ログに残し、次の回にまた確かめる)。開発中は確かめない
  - コマンドは、ウィンドウを出さず、入力なし(認証の入力を求めない)・時間制限(120秒)つきで実行する
  - 更新があれば、画面の上部(タブの列の下)に帯を出す(イベント `updateAvailable`。起動したときは `bootstrap` の `update`)。
    Windows の通知は出さない。「あとで」を押すと、次の起動までは出さない。
    更新がなくなったときも `updateAvailable` を出し(`available: false`)、出ている帯を消す。
    「更新して再起動」は、確認してから、入力中のコメントを下書きに保存し(保存が終わるのを待つ)、`Remi-update.bat /nopause` を最小化したウィンドウで起動する
    (バッチが Remi を終了し、取り込み、起動し直す)。`Remi-update.bat` がなければ、ボタンを押せない状態にして理由を出す
- 配布: PyInstaller。`--onefile` は起動のたびに一時展開して遅く、ウイルス対策ソフトに誤検知されやすいので、**`--onedir` + zip(または簡易インストーラー)を第一候補**にする

### 2.6 画面とバックエンドの接続

```
WebView2 ──HTTP──▶ ローカルAPIサーバー(127.0.0.1:ランダムなポート)
   │                 ├ GET  /             画面(index.html, CSS, JS)
   │                 ├ POST /api/<method> RPC(JSON)
   │                 ├ GET  /events       SSE(同期結果・通知クリックなど)
   │                 ├ GET  /attachments/<server_id>/<attachment_id>  キャッシュ済みの画像
   │                 ├ POST /upload       送信前の添付(Redmineへアップロード)。GET /pending/<id> でその画像を表示
   │                 └ GET  /external-image?url=…  外部画像(設定で許可した場合のみ)、GET /highlight.css  コードの色
   └─ pywebview: ウィンドウの表示・非表示、閉じる操作の横取り
```

- **認証**: 起動のたびにランダムなトークンを作り、最初のURLのクエリで渡す。サーバーは `HttpOnly; SameSite=Strict` のCookieに置き換えてから、トークンを含まないURLへリダイレクトする。以後はCookieがないリクエストを拒否する
- **DNSリバインディング対策**: `Host` ヘッダーが `127.0.0.1:<ポート>` でなければ拒否する。RPCは `POST` かつ `Content-Type: application/json` のみ受け付ける
- **Content-Security-Policy**: `default-src 'self'`(画像は `data:`、スタイルはインラインも許可)。外部の画像(設定で許可した場合)は、バックエンドが代わりに取得して配信する。インラインスクリプトは使わない
- RPCのメソッドは、Pythonの `RemiApi` クラスにまとめる。画面から呼べるのはこのクラスのメソッドだけ
- **開発モード**: `python -m remi --browser` で、ウィンドウを作らずに既定のブラウザで画面を開く(どのOSでも画面を開発できる)
- **テスト**: 同じローカルAPIサーバーを偽のRedmineにつないで起動し、Playwright(Chromium)で画面を操作して確認する。CIでも実行する

## 3. サーバー・プロジェクト階層とデータモデル

「サーバー > プロジェクト(親子階層) > チケット」で構造化する。チケットはツリーに入れず、中央の一覧に表示する。

### 3.1 マルチサーバー

- 設定項目: 名前、URL、APIキー、有効/無効、ポーリング間隔、通知ON/OFF、マイルストーンを表示する(プロジェクトの設定が「継承」のときの既定。§3.3)、プロキシ、**テキスト書式(Markdown / Textile / なし。§5.3)**
- 登録時に `GET /users/current.json` を呼び、URL・キー・自分のユーザーIDを検証する。所属グループも `include=memberships,groups` で取得しておく
- 接続テストでは、次の失敗を区別して表示する: 証明書エラー、401(キーが誤っている)、403/404・JSONでない応答(URLの誤り、またはREST APIが無効の可能性)、タイムアウト・プロキシの問題
- **URLの探索**: プロジェクトなどの画面のURLを入れてしまっても、接続テストが Redmine のトップのアドレスを探す。入力されたURLから、
  ①入力されたまま ②`/projects/` `/issues/` などの手前 ③区切り(`/`)ごとに短い方から(最大6階層まで)の順に、`/users/current.json` を試し、
  Redmine の応答(ユーザー)が返ったものを使う。見つかったURLが入力と違うときは、URLの欄をそれに直す(保存は、利用者が登録を押したとき。直したことは、画面に出さない)。
  404・403・JSONでない応答・5xx は次の候補へ進み、接続できない・証明書・タイムアウトなど、ホストそのものの失敗は、そのまま返す。
  APIキーを送るのは、入力されたホストの中だけ。どこにも見つからなければ、入力されたままのURLで接続テストの結果を返す
- 編集で接続先(スキーム・ホスト・ポート)を別のサーバーに変えたときは、APIアクセスキーも入力し直す(保存済みのキーを、
  新しい接続先へ送らない。接続テストの前に画面で求め、バックエンドも `key_required` で断る。同じホストの http → https は同じ接続先とみなす)
- 接続テストの表示は、成功は「接続できました。」だけ(ユーザー名・件数などは出さない)。失敗は、1行目に「接続できませんでした。」、
  2行目に確認すること(URLの確認とREST APIの可能性など。管理者への依頼は書かない)
- 画面の文言は、ユーザーに必要な情報だけを過不足なく伝える。内部実装の用語・例外名・技術的な理由は出さない(ログには残す)
- 同期に失敗したサーバーは、ツリーに原因と、次に再試行する目安(「約N分後に再試行します」)を出す。
  キーの誤り・権限がないときだけ、「サーバー設定を開く」ボタンも出す
- サーバーの登録・編集のダイアログは、外側をクリックしても閉じない(入力を消さないため。Escと閉じるボタンで閉じる)。
  保存できないときは、その理由(名前の入力・接続テスト)をフッターに出す。ダイアログが重なったとき、Escは手前の1つだけを閉じる
- ウィンドウの最小サイズは 900×680(会話欄を十分に見せるため)
- 登録済みのサーバーのAPIキーを替えるときも接続テストを必須にし、キーの持ち主(ユーザーID)を確かめる。
  URLまたは認証ユーザーが変わったら、そのサーバーのキャッシュ(チケット・journal・添付と画像キャッシュ・既読・下書き・
  プロジェクト・マスター・バージョン・通知の記録)を捨てて初回同期からやり直す。前のユーザーのプライベートノートなどを、別のユーザーに見せないため。
  同じユーザーのキーに替えただけなら残す。プロジェクト単位の設定(通知など)は利用者の好みなので残す
- **並び順**: サーバーの並び(`servers.sort_order`)は、ツリーと設定のサーバー一覧で共通。新しく登録したサーバーは最後に置く。
  並べ替えは、ツリーのサーバーの行、または設定のサーバー一覧の左のつまみ(⠿)をドラッグ&ドロップする(RPC `reorderServers`。
  無効なサーバーを含む、すべてのサーバーを新しい順に並べて渡す。並べ替えている間に追加・削除されたら断る)
  - 5ピクセル以上動かしたときだけドラッグを始める(ふつうのクリックと区別する)。落とす位置は青い線で示し、動かしている行は元の位置で薄くする
  - ツリーでは、ドラッグを始めたら、すべてのサーバーを折りたたんでサーバーの行だけにする(▶)。終わったら、ドラッグ前の開閉の状態に戻す
    (保存している開閉の状態 `tree_collapsed` は変えない)。ツリーには有効なサーバーだけが出るので、無効なサーバーは今の位置のまま残す
  - Esc を押す・並べ替えの範囲(ツリーのペイン・設定の一覧)の外で離すと、取り消す。「すべてのサーバー」の行は先頭に固定
  - 設定のサーバー一覧では、つまみにフォーカスして Alt+↑/↓ でも1つずつ動かせる。サーバーが1台だけのときは、つまみを出さない
- チケットは `(server_id, issue_id)` で一意にする
- ワーカーはサーバーごとに独立させる。1台が落ちても他に影響せず、バックオフもサーバー別に行う

### 3.2 プロジェクトツリー

- 取得: `GET /projects.json?limit=100&offset=…`。約6時間ごとに取得する(前回の取得時刻を保存し、起動のたびには取り直さない。§4.6)
- 表示範囲: 既定は「監視対象のチケットを含むプロジェクトとその祖先」。祖先が見えない場合は名前を薄く表示し、親そのものが返らない場合はルートとして扱う。サーバーごとに全プロジェクト表示にも切り替えられる(下のツリーのリンクから)
- 親を選ぶと、子孫のチケットもまとめて表示する。未読数も子の合計を親に集計する
- 特別ノード: 各サーバー直下に「すべて」と「未読のみ」、ツリー最上位にサーバー横断の「すべて」
- アーカイブ・閉鎖されたプロジェクトは `status` を保存し、既定では非表示にする

### 3.3 プロジェクト単位の設定(継承あり)

プロジェクトごとに次を設定できる。どの設定も **「親を継承 / オン / オフ」の3状態**で持ち、ルートの既定値は下の表のとおり。

| 設定 | ルートの既定 | 内容 |
| --- | --- | --- |
| `notify` | 継承(サーバー設定に従う) | 通知のON/OFF |
| `watch_versions`(画面の名前は「マイルストーンを表示する」) | サーバーの既定に従う(初期値はオフ) | 未完了のバージョン(ロードマップ)をツリーに表示して監視するか(§5.5) |

実際に使う値は、子から祖先へ順にたどって最初に見つかった「オン/オフ」とする。どこにも設定がなければ、サーバーの既定に従う
(`notify` はサーバーの通知の設定、`watch_versions` はサーバーの⚙ダイアログの「マイルストーンを表示する」。`servers.watch_versions`)。
ツリーのプロジェクトの行の右端の歯車ボタンから変更する
(右クリックメニューには設定を出さず、「すべて既読にする」「ブラウザで開く」などの操作だけにする。サーバーも同じ)。
プロジェクトの行の右端には「設定(歯車) | 表示するチケット(フィルタ)」のボタンを置く(サーバーの行にも置く。歯車はサーバーの設定を開く)。
右端にそろえるので、どの行でも縦にそろう。ボタンは、絞っているフィルタを除き、行にマウスを乗せたときに表示する。
件数は名前のすぐ右に、グレーの `(5)` で出す(バージョンは `(完了/全体)`)。未読・変化の印は青い丸だけで、太字や色文字にはしない。
親の行(畳んでいるときだけ)は、中の未読コメントやバージョンの変化も拾って丸を付け、開くと丸は実際の場所に移る。
未読になるのはコメントだけで、項目の変更・添付だけの更新は未読にしない。
「表示するチケット」はすべて外せる。表示するもの(チケット・ロードマップ)がないプロジェクトはツリーから消える
(サーバーの下の小さく薄い色の「すべてを表示」のリンク(表示中は「非表示に戻す」)で戻せる。「すべてを表示」でだけ出ているプロジェクトは、薄い色で表示する。サーバーが複数あるときは、2つ目以降のサーバーの上に薄い横線を入れる)。表示するチケットがない(プロジェクトが1つもない・すべてのフィルタを外した)サーバーには、プロジェクトが出ていても「すべて」「未読のみ」を出さない。

## 4. 同期設計

### 4.1 同期の基準時刻(サーバー時刻)

- PCの時計は使わない。**前回のレスポンスに含まれていた `updated_on` の最大値**を `last_sync_cursor` として保存する
- 次の問い合わせは `updated_on=>=(cursor − 2分)` と少し重ねる。重なって返ってきた分は、`updated_on` が保存済みの値と同じなら処理を飛ばす
- 日時はISO 8601(UTC)で送る。`>=` はURLエンコードする

### 4.2 対象チケットの取得

| 種類 | クエリ | 実行条件 |
| --- | --- | --- |
| 担当 | `GET /issues.json?assigned_to_id=me&status_id=*&updated_on=>=…&sort=id` | 常に実行 |
| ウォッチ | `GET /issues.json?watcher_id=me&status_id=*&updated_on=>=…&sort=id` | 常に実行 |
| 作成 | `GET /issues.json?author_id=me&status_id=*&updated_on=>=…&sort=id` | 「表示するチケット」に「自分が作成」を含むプロジェクトが1つでもある場合だけ |

- REST APIではOR条件が使えないので、クエリを別々に呼んでIDで統合する。各チケットに `relation_flags` を立てる
- 「作成」で取れたチケットは、そのプロジェクトの「表示するチケット」に「自分が作成」を含む場合だけ監視対象にする(判定はローカルで行う)。
  「表示するチケット」の既定は「自分が作成」を含まない(含めると通信が増える)。含めるプロジェクトが増えたら、初回同期からやり直す
- `limit=100` で `total_count` に達するまでページングする。並びは番号順(`sort=id`)にする
  (更新日時の順だと、取得の途中で更新されたチケットが末尾へ移り、後ろのものが前にずれて、ページの境目のチケットを取りこぼす)
- `assigned_to_id=me` には、自分が所属するグループへの割り当ても含まれる(サーバーの設定による)。グループ経由の担当も「担当」として扱い、一覧ではアイコンで区別する

### 4.3 履歴(journal)の取得

- 一覧APIでは `include=journals` が使えない。更新があったチケットだけ `GET /issues/{id}.json?include=journals,attachments` を個別に呼ぶ
- 毎回全履歴が返るが、journalは `journal_id` でupsertし、既存のものは更新しない(notesの編集に対応するため、内容が違えば更新する)
- 個別取得はキューに入れ、2.4のレート制御に従って順に処理する。今開いているチケットは、キューに並ばず、依頼の直後にいちばん先に取得する(画面の操作として。§2.4)

### 4.4 初回同期(数百件への対応)

1. 担当・ウォッチ(・作成)の一覧を、`updated_on` の条件なしで、**クローズ済みも含めて**(`status_id=*`)全件取得する(数百件ならページング数回で済む)。
   アプリを使い始める前にクローズされたチケットも、「クローズ済みを表示」で見られるようにするため。クローズ済みは `monitored=0` で保存し、通常の一覧には出さない(§4.7)。
   コメントは、他のチケットと同じく遅延取得する(監視対象外のものは、開いたときに取得する)
2. この時点で、すべてのチケットを「既読」として初期化する。初回登録で大量の未読や通知が出ないように、このフェーズでは通知を出さない
3. journalは**遅延取得**する。開いたチケットはすぐ取得し、それ以外は低優先度のキューでゆっくり埋める
4. 未読は、取得済みの journal だけで数える。journalをまだ取得していないチケットは、取得する(先読みで1秒に1件)までは未読に数えない

### 4.5 開いているチケットの監視

- 15〜30秒ごとに `GET /issues/{id}.json`(includeなし)で `updated_on` だけを確認する
- 変わっていたら `include=journals,attachments` で取得し直す

### 4.6 適応的ポーリング間隔

| 対象 | 間隔の目安 |
| --- | --- |
| 今開いているチケット | 15〜30秒(軽い確認のみ)。画面が見えていない(トレイに格納・最小化)間は確かめない |
| 監視対象全体(差分) | 3分 / 5分(サーバー設定。1分は設けない) |
| プロジェクト一覧・マスタ | 約6時間ごと。前回の取得時刻を保存し、起動のたびには取り直さない(持っていなければすぐ取得) |
| 自分のユーザー情報(所属グループ) | 起動時と約1時間ごと |
| 関係が外れたチケットの検出 | 約1時間ごと。そのほかに、差分同期のたびの件数の確認(違うときだけ)と、「今すぐ同期」で行う |
| 削除の検出 | 1日1回程度 |
| コメントの遅延取得(キュー) | 1秒に1件(サーバーごと) |

ウィンドウが非アクティブの間は間隔を延ばし(例: 2倍)、エラーが起きたら指数バックオフする(上限30分)。

**多数の利用者が同じRedmineを使う場合の負荷対策**(数百〜千人の利用を想定):

- 各間隔とバックオフに±15%のジッターを入れ、多数のクライアントの問い合わせが同じ時刻にそろわないようにする
- サーバーが 429(流量制限)・503 で `Retry-After` を返したら、その時間(最大1時間まで。異常に長い指定から守るため)は問い合わせない(運用側がリバースプロキシで
  流量を絞ったときに従う)。429 は再試行するエラー(`rate_limited`)として扱う
- 「今すぐ同期」(F5・同期ボタン・トレイ)は、前の「今すぐ同期」が終わるまで(どれかのサーバーが同期している間)は受け付けない。
  受け付けた間は、同期ボタンが回転し、下の状態欄に「同期しています…」を出す。押したときは「同期中です」と伝える。
  終わったら、待ち時間なしですぐ受け付ける(連打するものではないので、間隔は設けない)。同期の範囲は、差分取得・件数確認・
  突き合わせまで(コメントの先読みは含めない)。バックオフ中でも1回は試すが、失敗の回数は残すので、また失敗すれば前より長く待つ

### 4.7 関係が外れたチケット・クローズ済み・削除

- **関係が外れた**: 担当の変更やウォッチ解除は差分に出ない。約1時間ごとに、`updated_on` の条件なしの一覧(**未完了のみ**、`status_id=open`)を取り直し、IDを突き合わせる。どのクエリにも出なくなったチケットは `monitored=0` にする。
  1時間待たずに気づけるよう、次のときにも同じ突き合わせを行う
  - **差分同期のたびに、担当とウォッチの未完了の件数だけを確認する**(`limit=1` の2通信。`total_count`)。ローカルの監視対象の件数と違うときだけ、全件の突き合わせを行う。
    突き合わせても直らない同じ食い違いは、繰り返さない(件数が変わったら、また行う)。「自分が作成」は、プロジェクトで取得を絞っているので、件数の確認の対象にしない(1時間ごとの突き合わせで拾う)
  - **「今すぐ同期」**(F5・同期ボタン・トレイ)
- **クローズ済み**: ステータスが `is_closed` のチケットは、**すぐに `monitored=0` にする**(クローズ後に残す期間はない)。一覧・ツリーの件数・未読数には出ないが、
  キャッシュは残すので、一覧のステータスの絞り込みを「クローズ済み」か「すべて」にすれば閲覧できる。内容(件名・状態など)は、自分に関係があれば差分同期で更新する。
  コメントは先読み・通知をせず、開いたときに取得する。再オープンされたら、差分同期で監視対象に戻る。
  **使い始める前にクローズされたチケットも、初回同期で取り込む**(§4.4)。更新で初回同期の対象を広げたときは、スキーマのマイグレーションで
  `initial_sync_done` を戻し、使い始めている利用者も1回だけ初回同期をやり直す(キャッシュは消さない。既読・下書き・取得済みのコメントは残る)
- **削除**: 1日1回、監視対象のIDを個別に確認する(404なら削除とみなす)。50件ずつまとめて問い合わせる(まず一覧で見えるかを確かめ、見えなかったものだけ個別に404を確認する)
- **関係が外れた未完了のチケット**のキャッシュは、監視対象外になってから10日たったら削除する(1日1回。`issues.unmonitored_at` から数える)。
  次のものは残す: **クローズ済み**(過去のチケットを見返せるように)、ウォッチしているバージョンに含まれるもの、下書きがあるもの、
  10日以内に開いたもの。削除するときは、キャッシュした画像のファイルも消す。再び関係ができたときは、同期が取得し直す。
  サーバーを削除すれば、そのサーバーのキャッシュはすべて消える
- 個別のチケットの取得が 404(削除)・403(見えなくなった)のときは、そのチケットだけの問題として扱う(削除ならキャッシュを消し、
  見えなくなったなら監視対象外にする)。サーバー全体のエラー(バックオフ)にはしない

## 5. 画面構成

3ペイン構成。左のツリーで絞り込み、中央でチケットを選び、右で会話とコメント投稿を行う。
ツリーで別の項目を選ぶと、開いていた会話は閉じる(入力中の文章は下書きとして残る)。

```
┌──────────┬──────────────┬──────────────────────┐
│ サーバー/    │ チケット一覧    │ 会話ビュー                │
│ プロジェクト │ #123 件名 ●2 │ [ヘッダ: 件名/状態/担当]  │
│ ツリー      │ #98  件名    │  吹き出し(journal)       │
│ ⚙設定      │              │ [入力欄]        [送信]   │
└──────────┴──────────────┴──────────────────────┘
```

| チャット | Redmine |
| --- | --- |
| ワークスペース | サーバー |
| チャンネルグループ | プロジェクト(親子階層) |
| ルーム | チケット |
| メッセージ | journal(notesがあるもの) |
| システムメッセージ | ステータス・担当者などの変更履歴(notesのないjournal、またはdetails部分) |
| 送信 | `PUT /issues/{id}.json` の `notes` |
| 未読バッジ | 最終既読journal IDより新しく、**notesがあり、自分以外が書いた**journalの数 |

### 5.1 チケット一覧(数百件対応)

- 一覧はHTMLで描画する。数百件ならそのまま描画して問題ない。千件を超える場合に備えて、表示範囲だけを描画する仕組み(仮想スクロール)を入れられる構造にしておく
- 並び順の既定は「更新日時の新しい順」。「未読を上に」(全体の設定の画面にある。設定 `unread_first`、既定はオン)がオンのときは、
  選んだ並びの中で、未読のチケットを先頭に出す。
  会話を開いている間は、既読になったチケットの並びを動かさない(開いたチケットは既読になって下へ移り、↓で順に読むとき次の未読を飛ばすため)。
  ただし、並べ替え・絞り込み・検索・選択(プロジェクトなど)を変えたときは、固定せず、新しい並びにする。
  会話を閉じたら、既読になったものを並びに反映する。マウスを乗せると、時刻の代わりに「⋯」ボタン(未読に戻す・開く)を出す
- 関係で絞り込むボタン(すべて / 担当 / ウォッチ / 作成)を、ヘッダに常に出す。グループ経由の担当は「担当」に含める。選んだ状態は保存する
- **ヘッダの並び**: 1行目に場所(親のプロジェクトなどのパンくず。マイルストーンは「… › ロードマップ」)を小さく(11px)出し、
  2行目に名前(プロジェクト名・バージョン名)・ボタン・件数を並べる。場所が長くても名前の幅を削らないため。
  場所は、長ければ末尾を省く。場所がない(「すべてのサーバー」・サーバーを選んだ)ときは、1行目を出さない
- **ヘッダのボタン**: 名前の行の右に、検索(🔍)・並べ替え(⇅)・絞り込み(⏷)・表示密度(☰)のボタンを並べ、その右に件数を出す。
  検索=青(`--accent`)、絞り込み=緑(`--c-filter`)、並べ替え=紫(`--c-sort`)で、アイコンは、条件がないときも、それぞれの色。
  条件があるときは、背景と枠にも色が付く。ボタンに数字のバッジは付けない。検索・絞り込みの小さなウィンドウは、そのボタンをもう一度押すと閉じる
  (並べ替えのメニューも同じ)。担当者の「名前で探す」は、入力欄を作り直さない(日本語の変換を途切れさせない。一覧が更新されても、
  キーボードで項目を切り替えても、フォーカスは残る)。ウィンドウを開き直したときは、前の検索語を残さない
- **狭いとき**(一覧のペインが 300px 未満。最小は240px): ボタンの隙間を詰め、件数は数字だけにする
  (タイトルは1行で、収まらなければ「…」)。行は折り返さず、関係のラベル、並べ替えのタグの順に縮める(ステータス・番号・時刻は縮めない。
  時刻は午前・午後を省く)。絞り込みの大分類(未完了 / クローズ済み / すべて)の3つは、同じ幅で1行に並べ、「(既定)」は下に小さく出す
- **検索**: 🔍を押すと、ボタンの下に小さなウィンドウが開く(検索ボックスと、「Esc で閉じる、↓ で一覧へ」のヒント)。
  件名・番号で、入力するとすぐ絞り込む。Ctrl+F でも開いてフォーカスする。Esc は、検索語があれば消し、空なら閉じる。
  Enter・ウィンドウの外のクリックで閉じる(検索語は残り、チップになる)。検索語は設定 `list_search` に保存して、次回も使う
- **並べ替え**: ⇅のメニューで、項目(更新日時 / チケット番号 / 件名 / ステータス / トラッカー / 優先度 / 期日)と、昇順・降順を選ぶ。
  設定 `list_sort`(`{key, desc}`、既定は更新日時の降順)に保存する。項目を切り替えたときの順序の初期値は、更新日時と優先度が降順
  (優先度は高い順)、それ以外は昇順(期日は近い順)。同じ値のものは、更新日時の新しい順。期日のないものは、昇順でも降順でも最後。
  ステータス・トラッカー・優先度は、名前順ではなく、Redmine での順序(`masters.extra_json.position`。取得した順)で並べる。
  順序を知らないもの(マスターを取得し直す前)は、昇順でも降順でも最後に置く
- **並べ替えの値の見せ方**: 右側は、更新日時のまま。優先度・トラッカー・期日で並べているときは、1行目のステータスの隣に、
  薄い紫のタグ(`優先度 高め` / `トラッカー バグ` / `期日 11/25`、期日なしは `期日 なし`)を足す。ステータスで並べているときは、
  ステータスのラベルを同じ色にする。緊急(優先度)と期限切れの期日は、赤みの背景と濃い赤の文字(警告)にする
- **絞り込み**: ⏷のポップアップ(ペインの幅)に、ステータス・トラッカー・優先度・担当者・期日の項目を、横線で区切った見出しの行で並べる。
  見出しを押すと、その項目だけが開く(初期はステータスだけ)。見出しの右側に、いまの選択を出す(選択中は緑)。最下部に「すべて解除」。
  - ステータス: 先頭に「未完了(既定)/ クローズ済み / すべて」の3つ(`open` / `closed` / `all`。Redmine の「未完了・終了・すべて」に当たる。
    個別の「終了」と紛れないよう、「クローズ済み」と呼ぶ)。その下に、横線と補足を挟んで、個別のステータスをチェック付きで並べる。
    個別に選ぶと3つは選択なしになり(複数選べる)、3つを選ぶと個別は外れ、個別を全部外すと既定に戻る
  - トラッカー・優先度・期日(期限切れ / 今週 / 期日なし)・担当者: チェック付きのリスト(右に件数)。担当者だけ、「名前で探す」と、約5行のスクロール
    (「自分」「未割り当て」を先頭に固定。「自分」は、グループ経由の担当も含む)
  - 選択肢は、いまの一覧(検索・関係を当てたあと)にあるものだけ。件数は、その項目以外の条件を当てたあとの件数。選んでいる値は、0件でも残す
  - 属性は、サーバーごとに ID が違うので、名前で持つ。同じ項目の中は「または」、項目どうしは「かつ」
  - ステータスは、チケット一覧とマイルストーンで、別々に保存する(設定 `list_status`:既定は未完了、`version_status`:既定はすべて)。
    ほかの属性は、設定 `list_filter` に保存する。どれも次回も使う。ツリーの件数・未読数・トレイ・通知は、これらの絞り込みの影響を受けない
- **条件のチップ**: いま有効な条件を、ヘッダの関係ボタンの下に、✕付きのチップで並べる(検索=青、絞り込み=緑、並べ替え=紫)。
  ✕で、その条件だけを既定に戻す。右端の「すべて解除」は、既定から変えているものをすべて既定に戻す(検索・関係・ステータス・属性・並べ替え。
  「未読を上に」は触らない)。条件がなければ、行ごと出ない。関係は、ボタンが常に見えているので、チップに出さない
- **0件のとき**: 表示できるチケット(監視対象)があるのに、条件のために0件なら、「条件に一致するチケットはありません。」と出し、
  既定から変えた絞り込みがあるときは「すべて解除」ボタンを、ないときでステータスが既定の「未完了」なら
  「ステータスを「すべて」にする」ボタンを添える。チケットが1件もなければ、「チケットはありません。」。
  判定のため、`listIssues` は、0件のときに、条件を当てる前の件数 `scopeTotal` を返す
- **表示密度**(標準 / コンパクト): タイトル行の件数の隣のボタン(横線のアイコン)で切り替える。選んだ表示は設定 `list_density`
  (`standard` / `compact`、既定は標準。アプリ全体で1つ)に保存し、次回も使う。チケットの一覧とバージョンの一覧の両方に効く。
  コンパクトでは、件名を1行にして最新コメントを出さず、関係のラベルは3行目ではなく1行目(ステータスの隣)に出す。
  余白も詰める。未読(太字・バッジ)・選択中・ステータスは、標準と同じように見分けられる
- **表示するチケット**(自分が担当 / グループが担当 / ウォッチ中 / 自分が作成)を、**サーバーごとの既定**と
  **プロジェクトごと**に選べる。ツリーのサーバー・プロジェクトの横のボタン(絞っているものでは常に表示、ほかは
  行にマウスを乗せたときに表示)から選ぶ。プロジェクトのメニューでは、上で
  「親と同じ」(最上位のプロジェクトは「サーバーと同じ」)と「独自」を切り替え、独自のときだけ下のチェックを変えられる
  (親と同じのときは、引き継いでいる値をグレーアウトして表示する)。独自にしたときは引き継いでいた値から始め、
  親と同じに戻すと独自の値は消える。サーバーの既定の初期値はすべて表示。
  自分で設定したもののボタンは強調し、継承しているものは控えめに表示する。
  選んだ関係のどれかを持つチケットだけを一覧に出す。一覧の絞り込みボタン(全体で共通)は、各プロジェクトの
  表示するチケットの中での絞り込みとして使う(どのプロジェクトでも表示しない関係のボタンは隠す)。
  一覧の絞り込みボタンは、真ん中の一覧だけに効く。ツリーの件数・未読数、トレイの未読数、通知は、プロジェクトごとの「表示するチケット」
  だけで決め、絞り込みボタンの影響を受けない(ボタンを押すたびにツリーの数が変わらないように)。
  同期の対象は変えない
- 表示項目: 番号、件名、ステータス、更新日時、未読数、関係(担当/ウォッチ/作成/グループ担当)、最新コメントの冒頭

### 5.2 会話ビュー

- モックと同じHTML/CSSで描画する(吹き出し、日付の区切り、「ここから未読」、システムメッセージ)
- 上へスクロールして読んでいる間に他の人の新着が届いたら、会話の右下に「新着 N 件 ↓」ボタンを出す(押すと最下部へ移動する)。
  別のチケットを開いて表示まで少し時間がかかるときは、「読み込んでいます…」を出す。読み込みに失敗したときは、原因と「もう一度読み込む」ボタンを出す(読み込みが重なったときは、最新の応答だけを表示する)
- journalが多いチケットでは、最新の50件だけを表示し、「さらに読み込む」で過去分を追加する
- プライベートノートには鍵マークを付ける
- 変更履歴(details)は、小さな灰色の文字で表示する。1回の更新(journal)でまとめて行われた変更は1つにまとめ、
  「誰が・いつ」を1回だけ出して、変更を1行ずつ並べる(同じ人が何度も変更したように見えないように)
- ヘッダの日時は「チケットの最終更新」(Redmine上の `updated_on`)。アプリが情報を取得した日時は、ツリーの下の「最終同期」に出す
- ペインの幅は、利用者が仕切りを動かしたとき以外は変えない(表示中のチケットの内容で幅が変わらないようにする)。
  一覧と会話の間の仕切りを動かしても、ツリーの幅は変わらない

### 5.3 本文の表示(Markdown / Textile)

コメント本文と説明は、**サーバーごとのテキスト書式設定**に従って、MarkdownまたはTextileとしてレンダリングする。

#### 書式の設定(サーバー単位)

`servers.text_format` に次のどれかを保存する。

| 値 | 対応するRedmineの設定 | 使うライブラリ |
| --- | --- | --- |
| `common_mark` | 「CommonMark Markdown (GitHub Flavored)」(Redmine 5以降)。旧「Markdown」(Redcarpet)もこれで代用する | `markdown-it-py`(表、取り消し線。タスクリスト・自動リンクは自前で処理する) |
| `textile` | 「Textile」 | `textile`(python-textile) |
| `plain` | 「なし」 | 使わない(エスケープ + 改行保持 + URLの自動リンクのみ) |

- Redmineのテキスト書式は、一般ユーザーにはAPIで取得できない。そこで、**サーバー登録画面で選択**してもらう
- 登録時に、監視対象のチケットの最近のコメントを数件取得して記法を推測し(` ``` ` や `![…](…)` があればMarkdown、`!…!` や `h2.` や `<pre>` があればTextile)、その結果を初期値として提案する。最終的な決定はユーザーが行う
- あとからサーバー設定で変更でき、変更すると表示中の会話ビューも描き直す

#### レンダリングの流れ

```
本文(生テキスト)
  → 前処理: Redmine独自記法を、安全なプレースホルダーに置き換える
  → MarkdownまたはTextileでHTMLに変換する
  → サニタイズ(nh3): 許可したタグ・属性以外を取り除く
  → 後処理: プレースホルダーをリンク・画像に戻し、コードブロックをハイライトしたHTMLに差し替える
  → 画面へ返す(画面側では、このHTMLを吹き出しの中にそのまま入れる)
```

- 変換結果は `(server_id, journal_id, text_format, notesのハッシュ)` をキーにメモリ上でキャッシュする
- サニタイズは必須とする。Redmineのコメントは誰でも書けるので、生のHTML(Textileは`<…>`を通すことがある)をそのまま表示しない
- 画像の `src` はローカルAPIサーバーの `/attachments/...` に書き換える。CSPにより、画面が外部へ直接アクセスすることはない
- レンダリングはPython側で行う(画面側にMarkdown/Textileのライブラリを持たない)

#### Redmine独自記法

MarkdownとTextileの標準にはない、Redmineの記法を前処理で扱う。

| 記法 | 表示 |
| --- | --- |
| `#123` | チケットへのリンク。同じサーバーで監視中ならアプリ内で開き、それ以外はブラウザで開く |
| `##123`、`###123` | `#123` と同様に扱う(Redmineではプレビュー付きのリンク) |
| `#123#note-5`、`#note-5` | 該当するコメントまでスクロールする |
| `attachment:file.png` | 添付ファイルへのリンク(画像ならサムネイル) |
| `@login`、`user#5`、`user:login` | ユーザー名を強調表示する。自分宛てなら目立つ色にする |
| `r123`、`commit:abc`、`[[Wiki]]`、`document#1`、`version#1` など | サーバー上の該当ページへのリンク(ブラウザで開く) |
| `{{collapse(…)}}`、`{{toc}}`、`{{child_pages}}` などのマクロ | `collapse` は中身を展開して表示する。それ以外は灰色で `{{マクロ名}}` と表示する |
| `!` や `\` によるエスケープ(`!#123` など) | リンクにしない |

コードブロックの中では、これらの記法を解釈しない。

#### 自動リンクにするURIスキーム

- http / https / mailto は常にリンクにする。そのほかのスキームは `src/remi/link_schemes.json` で指定する
  (`form` が `//` なら「スキーム://」の形だけ、`:` なら「スキーム:」の形もリンクにする。`confirm` で開く前の確認)
- javascript / data / vbscript / about / blob は、指定してもリンクにしない。リンク・コードの中は変えない
- 押すと、Windowsでそのスキームに関連付けられたアプリで開く(ShellExecute)

#### 表示上の扱い

| 要素 | 対応 |
| --- | --- |
| コードブロック | 等幅フォント・背景色付き。言語指定があれば、Pygmentsでハイライトする(色はテーマのCSSで切り替える) |
| インラインコード | 等幅フォント + 背景色 |
| 表 | 枠線付き。幅が広い場合は横スクロールする |
| タスクリスト | `☐` / `☑` で表示する |
| 引用 | 左に線の入ったブロック |
| 見出し | 会話ビューの中では、サイズを一段控えめにする |
| 文字色・背景色(Textileの `%{color:red}…%`) | `color` と `background-color` だけ許可する |
| 脚注・定義リストなど | 変換結果をそのまま表示する |

#### 入力欄(投稿時)

- 投稿される本文は、入力したテキストのままとする(サーバー側でレンダリングされる)
- 入力欄の上に「編集 / プレビュー」タブを付け、プレビューは表示と同じレンダラーで描画する
- 入力欄は等幅フォントにはしないが、Tabキーでのインデント入力を可能にする(Escを押したあとのTabは、インデントではなく次の項目へ移る)

**画像**

| 記法 | 例 |
| --- | --- |
| Textile | `!image.png!`、`!>image.png!`、`!image.png(説明)!` |
| Markdown | `![説明](image.png)` |
| 添付への参照 | ファイル名が、チケットの添付(`include=attachments`)と一致すれば添付として解決する |
| 外部URL | `http(s)://` の画像は**既定では読み込まない**(リンクだけ表示)。設定で許可できる(下記の制限つき) |

- 添付画像は `content_url` からAPIキー付きで取得し、`%LOCALAPPDATA%\Remi\cache\attachments\{server_id}\{attachment_id}` に保存する
- 取得は同期ワーカーのキューで非同期に行う。取得前はプレースホルダーを表示し、取得できたら会話ビューを更新する
- 表示幅は最大でビュー幅程度まで縮小する。クリックすると原寸画像を別ウィンドウ(または既定のビューア)で開く
- 制限: 1ファイル10MBまで(超えたらリンクだけ表示)。キャッシュの合計は既定で500MBとし、古いものから削除する
- 対象: `image/png`、`jpeg`、`gif`、`bmp`、`webp`。SVGは表示しない
- 外部画像の取得先の制限(本文中のURLで、利用者のPCから意図しない接続先へアクセスさせないため):
  名前解決した後のIPアドレスが、ループバック・リンクローカル(クラウドのメタデータサービスを含む)・未指定・
  マルチキャスト・予約済みなら取得しない。プライベートIPアドレス(社内サーバー)は許可する。
  リダイレクトは自動で追わず、移動先も同じ検査をしてから取得する(最大3回)
- コメントで参照されていない添付(journalのdetailsにある `attachment` の追加)は、ファイル名のリンクとして表示する。画像なら小さく表示する

### 5.4 Redmineのページを開く(未対応機能の逃がし方)

- 会話ビューのヘッダに「Remiで開く」ボタンを置く(開く場所の設定に従う。「外部ブラウザ」にしているときは、外部ブラウザで開く)。コメントから開いたときは、そのコメント(`#note-N`)の位置へ移動する
- Redmineは `X-Frame-Options: SAMEORIGIN` を返し、Remi側もCSPで埋め込みを禁止しているため、右ペインへの埋め込みはしない
- 開く場所は設定 `redmine_open_in` で選ぶ
  - **Remiのタブ(Windowsのみ。既定)**: ウィンドウ全体のタブとして表示する。タブにできない環境では、別のウィンドウ→既定のブラウザの順に戻る。
    - 一番上にタブの列を置く。左端は固定の「Remi」(本体の画面。閉じられない)、その右にRedmineのタブを並べる。
      Redmineのタブがないときは、タブの列を出さない(これまでと同じ画面)
    - Redmineのタブを選んでいる間は、本体の画面を「タブの列と操作行」の高さだけにして、残りを、そのタブの WebView2 に使う。
      本体の画面(pywebview の WebView2)と同じ設定(データの保存先)を使うので、ログイン状態・保存したパスワードは共通になる
    - 操作行: 戻る・進む・再読み込み、URLの表示(入力はできない)、「別ウィンドウへ」。タブは「×」・中ボタン・Ctrl+W で閉じる。
      ページ内の「新しいウィンドウで開く」リンクは、新しいタブで開く
    - Redmineのタブを選んでいる間は、本体の画面が「タブの列と操作行」の高さだけになるので、本体の画面に重ねて表示する要素
      (ダイアログ・メニュー・画像の拡大・通知)は隠す(残骸を出さない)。「Remi」のタブに戻ると、そのまま戻る
    - 別のウィンドウのタイトルバーも、本体と同じく、アプリのテーマ(ライト/ダーク)の色にする
    - 「別ウィンドウへ」は、タブを閉じて、同じURLを新しいウィンドウで開く(ページの履歴・入力途中の内容は引き継がない。
      ログイン状態は共通)。切り離したウィンドウにも、同じ操作行(戻る・進む・再読み込み・URL・「タブに戻す」)を足す。
      操作行は、Windows の標準のボタンではなく、ウィンドウのページの上に置いた別の WebView2(`web/chrome.html`)で描く
      (アプリの画面と同じ HTML・CSS なので、ライト/ダークに追従し、記号は SVG の図形でフォントに左右されない)。
      ページの状態(URL・戻る/進む・読み込み中)は、イベント `windowState` で、ボタンの操作は API `windowAction` でやり取りする
      「タブに戻す」は、そのウィンドウを閉じて、同じURLをタブで開く。ドラッグでの切り離し・合体は、今は対応しない
    - 状態(タブの一覧・選択中・題名・URL・戻る/進む)は、Windowsに依存しない部品(`system/tabs.py`)で持ち、画面へは
      イベント `tabsChanged` で知らせる。WebView2 を扱う部分(`system/tabs_win.py`)は Windows 専用で、作れなかったとき・
      タブを開けなかったときは、別ウィンドウ→既定のブラウザの順に戻す
  - **Remiのウィンドウ(別のウィンドウ)**: pywebviewで専用のウィンドウを1つ開き、2回目以降は使い回す。WebView2のデータを `%LOCALAPPDATA%\Remi\webview` に保存するので、Redmineへのログインは最初の1回で済む(Windows統合認証のSSOなら、ログイン操作も不要な場合がある)
  - **外部ブラウザ**(既定のブラウザ): 普段のブラウザのログイン状態を使える
- Shift+クリック、または「▾」メニューの「外部ブラウザで開く」で、設定に関係なく外部ブラウザで開く。
  メニューの名前は「Remiで開く」(タブ・別ウィンドウ)と「外部ブラウザで開く」にそろえる(一覧の「⋯」・右クリック・ツリー・ヘッダ共通)。
  設定が「外部ブラウザ」のときは、「外部ブラウザで開く」の1つだけにする。設定の選択肢は「Remiのタブ(既定)」「Remiの別ウィンドウ」「外部ブラウザ」。メニューには「URLをコピー」も置く
- Redmineのページにはバックエンドの機能(API)を公開しない。Redmineのページからローカルサーバーへのリクエストは、Cookie(SameSite=Strict)とHostヘッダーの検査、JSON以外の拒否で防ぐ
- 本文中のリンクのうち、同じRedmineサーバーへのリンクは同じ方法で開き、外部サイトへのリンクは外部ブラウザで開く
- 左ペインは幅を可変にし、ツリーの折りたたみ状態とペインの幅を保存する

### 5.5 ロードマップ(バージョン)の監視

自分と関係するチケットとは別に、プロジェクトのバージョン(ロードマップ)の変化を追えるようにする。

- プロジェクトの設定「マイルストーンを表示する」(継承あり。§3.3。サーバーの⚙ダイアログに既定がある)をオンにすると、そのプロジェクトと
  子プロジェクトのバージョンを監視する。ほかのプロジェクトから共有されたバージョンは、持ち主のプロジェクトを
  ウォッチしているときだけ扱う
- ツリーでは、バージョンを新しいものから並べる。子プロジェクトがあるプロジェクトだけ、子プロジェクトと混ざらないよう
  「ロードマップ」(開閉できる見出し)の下に並べ、子プロジェクトがなければプロジェクトの直下に並べる。
  バージョンの旗は、開閉の ▼ と同じ場所に置く
  (Redmineと同じく上に新しいもの。期日の遅い順で、期日のないものは先頭、同じならIDの大きい順)
  (完了数/全体を表示)。終了したバージョンは、既定で畳んだ「終了したバージョン」の下に出す。
  バージョンが1つもないプロジェクトには「ロードマップ」を出さない。一覧のステータスの絞り込みは、チケットの一覧とは別の設定
  (`version_status`、既定は「すべて」)で、「未読を上に」は使わない。検索・並べ替え・属性の絞り込みは、チケットの一覧と同じ(関係の絞り込みはない)
- 同期: ウォッチしているプロジェクトのバージョン一覧(`/projects/:id/versions.json`)と、各バージョンのチケットの
  一覧(`fixed_version_id` で絞った `/issues.json`)を、ポーリング間隔(最短5分)ごとに確かめ、前回と比べて
  変化を記録する。先にすべてのプロジェクトのバージョン一覧を取り、チケットは未完了のバージョンについて、新しい
  (IDの大きい)ものから順に取得し、取得できたバージョンから1つずつ画面に反映する。
  バージョン一覧を保存した時点で、チケットの取得を待たずに画面へ知らせる(バージョンは `(…)` つきで先に出る)。
  プロジェクトの設定(またはサーバーの既定)で「マイルストーンを表示する」を変えたときは、チケットの差分同期を省いて、バージョンの取得だけをすぐ始める
  (同期の刻みも待たない)。取得している間は、そのプロジェクトの名前の横に小さな回転する印を、ツリーの下の状態欄に
  「ロードマップを取得しています…」を出す(最初の取得では「チケットを取得しています…」)。取得が終わるか、
  接続エラーになると消える。ほかにも、読み込みに時間がかかる場面(チケットを開いたときのコメント・選択肢・詳細、
  終了したバージョンの取得、送信、アップロード、プレビュー、接続テスト、「今すぐ同期」)には、同じ回転する印を出す
  **終了したバージョンのチケットは自動では取得せず、画面でそのバージョンを開いたときに取得する**(`fetchVersion`。
  見る機会が少ないうえ、終了したバージョンが数千あると取得に非常に時間がかかるため)。開いたときは、まだ取得して
  いなければ全件を取り、取得済みなら署名を確かめて変わっていたときだけ取り直す。まだチケットを取得していない
  バージョンは、ツリーで件数を「…」と表示する。未完了のバージョンは、まず「件数と最新の更新日時」(署名。`limit=1&sort=updated_on:desc`)だけを
  取得し、変わっていたときだけ全件を取り直す(追加・状態の変更は updated_on を進め、外れた・削除は件数を減らす)。
  updated_on は秒単位なので、最新の更新が前回の全件の取得から5分以内なら署名を信用せずに取り直し、署名が
  変わらなくても6時間ごとに全件を取り直す。取得済みのバージョンが終了・再開したときは、そのときに1回取り直す。
  プロジェクト・バージョンを最初に取得したときは、その状態を基準にして変化は記録しない
- 記録する変化: バージョンの作成、チケットの追加・外れた・完了・再開、期日・ステータス・名前の変更
- バージョンを選ぶと、一覧にそのバージョンのチケット(自分と関係ないものを含む。ステータスの絞り込みに従う)を、
  会話ビューの位置に期日・進捗と変化の記録を表示する。まだ見ていない変化があるバージョン(と、畳んでいる
  ロードマップ)には印を付け、表示したら消す。通知は出さない
- 自分と関係ないチケットは、監視対象外(relation_flags = 0)として保存し、ほかの一覧の件数・未読数・トレイ・通知には
  含めない。コメントは開いたときだけ取得し、未読として扱わない。表示をやめたら、そのバージョンの記録は消す

- Redmineのページを開くウィンドウでは、標準的なブラウザと同じく、パスワードの保存と自動入力、右クリックメニュー、
  ブラウザのショートカットを有効にする(WebView2 の設定。pywebview が出していないので、ウィンドウの中の部品から変える。
  `src/remi/system/webview2.py`)。保存したパスワードは WebView2 のデータ(DPAPIで暗号化)に残る。
  Redmineのログインは「ブラウザを閉じるまで」のCookieなので、終了後もログインしたままにするには、
  Redmineのログイン画面の「ログインを維持」を使う

## 6. コメント・編集・添付

ブラウザを開く場面を減らすため、よく使う操作はRemiの中でできるようにする。

### 6.1 コメント

- 投稿: `PUT /issues/{id}.json` に `{"issue": {"notes": "...", "private_notes": false}}` を送る
- 送信時に「プライベート」チェックボックスを付ける(既定オフ)
- 入力欄: Ctrl+Enterで送信、Enterで改行する
- 送信に成功したら、すぐにそのチケットを再取得して会話ビューに反映する
- 送信に失敗したら、`drafts` に本文を残し、「再送」ボタンを表示する
- 入力中の下書きはチケットごとに自動保存し(入力が止まって600ms後。チケットを切り替えるときは、待たずにすぐ保存する)、チケットを切り替えても残す
- **保存状態の表示**: 入力欄の下の操作行に、状態を小さく出す。通常は何も出さない
  - 入力した直後は「保存待ち」、保存しているあいだは「保存しています…」
  - 保存できたら「✓ 下書き保存済み」を出して、約2秒で消す。本文が空(下書きが残らない)のときは出さない
  - 保存に失敗したら「⚠ 下書きを保存できませんでした」と「再保存」ボタンを出す(次に保存できるまで残す)
  - 入力のたびに保存の世代を進め、古い保存の結果では、新しい状態の表示を上書きしない。送信を始めたとき・下書きを捨てたときは、表示を消す
  - 「コメントを送信できませんでした」(送信の失敗)とは別の表示にする
- 入力欄の上の「編集 / プレビュー」の右に、テキスト書式の名前(`Markdown` など)だけを出す(サーバーの設定であることは、マウスを乗せたときの `title` に出す)
- コメントは追記なので、基本的に競合しない

### 6.2 項目の変更(ステータス・担当者・優先度)

- 会話ビューのヘッダのドロップダウンで変更する。選んだ変更はすぐには送らず、入力欄の下に「ステータス: 新規 → 解決」のようなチップで表示し、**コメント・添付と一緒に「送信」で1回の更新として送る**(Redmineの編集フォームと同じ。変更だけを送ることもできる)
- 選択肢
  - ステータス: `GET /issues/{id}.json?include=allowed_statuses`(Redmine 5.0以降)で、ワークフロー上遷移できるものだけを出す。それ以前のRedmineでは全ステータスを出し、遷移できなければサーバーのエラーを表示する
  - 担当者: `GET /projects/{id}/memberships.json` のユーザーとグループ。先頭に「(なし)」「自分に割り当て」(ショートカット)を置き、そのあとに自分を含むメンバーを並べる(Redmineと同じ。
    担当が自分のときは、現在値に自分の名前を出す)。メンバー一覧は10分間キャッシュする
  - 優先度: マスタ(`/enumerations/issue_priorities.json`)
- 選択肢はRedmineへの問い合わせを伴うので、会話の表示とは別に読み込み、読み込むまではドロップダウンを操作できないようにする
- 送信後は、遷移できるステータスが変わるので選択肢を読み直す。ほかの人の更新が届いたとき(チケットの更新日時が変わったとき)も、
  今の値と選択肢(「詳細」の値も)を読み直す(送信前の変更は残す)
- 書き込めない操作の入力欄は無効にし、理由をツールチップとヘッダの注記で示す。判定はRedmineに合わせる
  (`Issue#attributes_editable?` / `notes_addable?`)
  - 終了したプロジェクトのチケット: 何も書き込めない
  - 自分のロール(`GET /users/current.json?include=memberships`、グループ経由を含む)の権限(`GET /roles/{id}.json`)で、
    項目の変更は `edit_issues`(自分が作成したチケットなら `edit_own_issues`)、コメントは `add_issue_notes`、
    プライベートコメントは `set_notes_private` を見る。添付は項目の変更かコメントができればできる。管理者は何でもできる。
    ロールと権限は10分間キャッシュする
  - ワークフロー上、今のステータスから移れる先がなければ(Redmine 5.0以降)、ステータスだけ変えられない
  - 親チケットの変更は `manage_subtasks`、ウォッチの追加・解除は `add_issue_watchers` / `delete_issue_watchers` も要る
  - トラッカーの設定(標準項目)で担当者を使わないときは、担当者を変えられない(`GET /trackers.json` の
    `enabled_standard_fields`。Redmine 5.0 以降。10分間キャッシュする)
  - メンバーでないプロジェクト(公開プロジェクトの非メンバー)や、問い合わせに失敗したときは権限が分からないので
    制限しない(できなければ送信時にRedmineが拒否する)。ワークフローの読み取り専用の項目はAPIから分からないので、
    同じく送信時の拒否に任せる

#### 詳細(ほかの項目)

- ヘッダの「詳細」を開くと、トラッカー・カテゴリ・対象バージョン(未完了のもの)・親チケット・開始日・期日・進捗率・
  予定工数と、チケットに適用されるカスタムフィールドを表示する。開いた状態はすべてのチケットで共通に覚える
  (設定 `issue_details_open`)。値と選択肢は、開いたときにRedmineへ問い合わせる
- Redmineと同じく、トラッカーの設定(標準項目)で使わない項目(カテゴリ・対象バージョン・親チケット・開始日・期日・進捗率・
  予定工数)は出さない(`enabled_standard_fields`。分からないときは、すべて出す)。カスタムフィールドは、Redmineが
  チケットに返すもの(そのトラッカー・ロールで使えるもの)だけが出る
- 文字列のカスタムフィールドの値が1つのリンク(本文の自動リンクと同じ種類: `http(s)://`・`www.`(https を補う)・`mailto:`・
  `link_schemes.json` のスキーム)なら、入力欄の右に「リンクを開く」ボタンを出す。入力欄は今までどおり編集でき、
  入力のたびにボタンの表示を切り替える。押すと、本文のリンクと同じ開き方(Redmineのページは設定に従い、それ以外のhttp(s)は
  外部ブラウザ、ほかのスキームは確認してから関連付けられたアプリ)。Shift+クリックで、常に外部ブラウザ。
  Redmineのページかは、サーバーのURLの直後が区切り(`/` `?` `#`)か末尾であることで判定する
  (`https://redmine.example.com.evil.net/` のような、前方だけが一致するURLを、Redmineとして開かない)
- 変更はステータスなどと同じく「送信前の変更」として持ち、送信時にコメントとまとめて1回の更新で送る
- カスタムフィールドの形式と選択肢は `/custom_fields.json`(管理者だけが取得できる)から得る。取得できない場合と、
  長文・リンク・添付などの形式は表示だけにする。ワークフローで読み取り専用にした項目はRedmineが無視するので、
  送った後の値で確かめる

#### コメントの編集・削除、添付の削除

- コメントは吹き出しの「⋯」メニューから編集・削除できる(Redmine 5.0 以降の `PUT /journals/:id.json`)。
  できるのは、Redmineと同じく「注記の編集」(すべて)・「自分の注記の編集」(自分のもの)の権限があるとき。
  削除は本文を空にして送る(項目の変更も行った更新なら、本文だけが消える)
- 添付ファイルは、チケットを編集できる人だけが削除できる(`DELETE /attachments/:id.json`)
- チケットを取り直したとき、Redmineで削除されたコメント・添付は手元からも消す

### 6.3 添付ファイル・画像の貼り付け

- Redmineと同じく、入力欄に**クリップボードの画像を貼り付ける**と添付になり、本文の書式に合わせて画像の記法を入れる(Markdown: `![](name.png)`、Textile: `!name.png!`)
- 貼り付けた画像の名前は、Redmineと同じ `clipboard-YYYYMMDDHHMM-xxxxx.png` の形式にする
- 「ファイルを添付」ボタンとドラッグ&ドロップでも添付できる(画像以外は本文に記法を入れない)
- 添付した時点で `POST /uploads.json` でアップロードしてトークンを受け取り、送信時に `uploads` として渡す
  - 画面からは、ローカルサーバーの `POST /upload` に送る。CSRF対策として、専用ヘッダー(`X-Remi-Upload: 1`)が付いたリクエストだけを受け付ける
  - 送信前の画像は `/pending/<id>` で表示し、プレビューにも反映する
- 添付はチップで表示し、×で取り消せる(取り消すと本文の記法も消す)
- ファイルサイズの上限はRedmineの設定に従う。超えた場合はRedmineのエラーを表示する。
  ローカルサーバーが受け取れるのは50MBまで(`uploadMax`)。それより大きいファイルは送らず、チップに「50MBより大きいファイルは添付できません」と出す
- 本文の画像の記法のファイル名は、Markdown の変換で `%20` などに置き換わる(`![](<スクリーンショット 1.png>)`)。添付と照合するときは、
  元の文字に戻してからも照合する(スペース・日本語を含む名前の画像も表示する)

### 6.4 ウォッチ

- ヘッダの「ウォッチする / ウォッチ中」ボタンで、自分をウォッチャーに追加・削除する(`POST /issues/{id}/watchers.json`、`DELETE /issues/{id}/watchers/{user_id}.json`)
- ローカルの関係フラグにもすぐ反映する。担当でもウォッチでもなくなったチケットは監視対象外になる。
  クローズ済みのチケットは、ウォッチしても監視対象にしない(未読・件数の対象外のまま)

## 7. 既読・未読・通知

### 7.1 既読

- **チケットを会話ビューで開いた時点で**、その時点の最新journal IDまでを既読にする
- 開いている間に新しいjournalが届いた場合、ウィンドウがアクティブならすぐに既読にする。非アクティブなら、次にウィンドウがアクティブになった時点で既読にする。
  上へスクロールして読んでいる間に届いたものは、最下部まで見たとき(「新着」ボタンを押したときを含む)に既読にする
- 一覧の右クリックで「未読に戻す」「すべて既読」を使えるようにする
  - 「未読に戻す」は、自分以外が書いた最後のコメントの直前まで既読位置を戻す(自分のコメントは未読として数えないため)。
    自分以外のコメントがない・未読として数えない(クローズ済みなど)・すでに未読のチケットでは、押せない状態にする

### 7.2 未読・通知の対象

- **未読バッジと通知の対象**: notesがあり、自分以外が書いたjournal
- **変更履歴のみのjournal**: 会話ビューにシステムメッセージとして表示するだけで、未読数にも通知にも含めない
- **クローズ済みは、未読の対象外**: クローズ済み(`monitored=0`)のチケットは、ツリー・トレイ・通知・「すべて既読にする」と同じく、
  一覧にも未読(太字・バッジ)を出さず、「未読のみ」にも出さない(開いたときに取得するので、既読にする手段がない未読を見せない)。
  「すべて既読にする」は、監視対象のチケットを、保存済みの最新のコメントまで、1回のSQL(1つのトランザクション)で既読にする。既読位置は戻さない

### 7.3 通知

- ON/OFFの判定はグローバル → サーバー → プロジェクト(継承あり)の順で行う。将来はチケット単位のミュートも追加できる
- 自分のコメントでは通知しない。表示中(ウィンドウがアクティブで開いている)のチケットでも通知しない
- 初回同期では通知しない(4.4)
- 「表示するチケット」から外れたチケットでは通知しない(5.1)。真ん中の一覧の絞り込みボタンは通知に影響しない
- 1回の同期で複数件あった場合は、「#123 他3件の新着コメント」のようにまとめて1回だけ通知する
- 実装: `windows-toasts` でWindowsのトースト通知を出す。通知をクリックすると、そのチケットを開いた状態でウィンドウを前面に出す
- 通知は、アプリと同じ AppUserModelID(`Remi.Remi`)で出す。起動のたびに `HKCU\Software\Classes\AppUserModelId\Remi.Remi`
  (表示名・アイコン)と、`remi:` プロトコル(`HKCU\Software\Classes\remi`。`<exe> --open "%1"`)を登録し直す
  (管理者権限は不要)。登録していないIDで出すと、トーストが消えた後の通知センターの履歴から押してもアプリに届かない
- 通知を押すと `remi://open?server=<ID>&issue=<ID>` を開く(プロトコル起動)。履歴から押したとき・アプリを終了した後でも、
  Remiが起動して(起動中なら2つ目のプロセスが多重起動防止のパイプで依頼を渡して終わる)そのチケットを開く。
  URLはだれでも開けるので、この形以外は受け付けない。表示中のトーストを押したときは、すぐ開けるようプロセス内でも開く
- 通知はチケットごとに1つにする(タグ `<サーバー>-<チケット>`、グループ `s<サーバー>`)。同じチケットの新しい通知は
  前の通知を置き換え、アプリでチケットを読んだら(すべて既読を含む)、そのチケットの通知を通知センターから消す
- 一度通知したコメントは、二度と通知しない(`notified` テーブル。チケットのキャッシュとは別に残すので、
  監視対象から外れて戻った・削除の確認などでキャッシュを消して取り直しても、同じコメントを再び通知しない)。
  接続先・認証ユーザーを変えたときは、ほかのキャッシュと一緒に捨てる(別のサーバーの同じ番号のチケットの新着を、通知しなくならないように)
- クローズ済み・関係が外れた(監視対象外の)チケットのコメントは、先読みも通知もしない(開いたときに取得する)。
  そのとき届いたコメントは、通知の対象として扱ったことにする(再オープンで監視対象に戻ったときに、古いコメントをまとめて通知しない)
- トレイアイコンには、未読があることを示すバッジ付きのアイコンを表示する

## 8. トレイ常駐・自動起動

- トレイアイコンは `pystray` で表示する(専用のスレッドで動かす)。アイコン画像はPillowで描画し、未読があるときはバッジを付ける
- ×ボタンで**初めて**トレイに格納するときだけ、「Remiはトレイで動作しています」と通知する(終了したと思われないように。2回目以降は出さない)。
- ×ボタンではトレイに格納し(pywebviewの `closing` イベントで閉じる操作を取り消してウィンドウを隠す)、終了はトレイメニューから行う
  Redmineを開いたウィンドウも、本体と一緒に隠し、本体を開いたときに戻す(本体だけが消えて、Redmineのウィンドウが残らないように)
- 自動起動は `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` に、exeのパスを登録する(設定でON/OFF)

### 8.1 定期的なタスク

Remi が動いている間だけ、決まった間隔でコマンドを実行する仕組み(`system/scheduled_tasks.py`)。**設定するのは開発者だけ**で、利用者には開放しない
(画面からは変えられず、配布フォルダにも書き換えられる設定ファイルとしては置かない)。

- 設定は、リポジトリの `src/remi/scheduled_tasks.json` に書く。**このファイルがなければ、何も実行しない**。
  書き方の見本は `src/remi/scheduled_tasks.sample.json`(これは読まない)。使うときに、コピーして `scheduled_tasks.json` という名前で置く
  (`scheduled_tasks.json` は `.gitignore` に入れてある)
- 配布物(exe)では、ビルド(`tools/build.py`)が `scheduled_tasks.json` を Python のモジュール(`remi_scheduled_tasks_embedded`)にして、
  exe の中に埋め込む。書き方に誤りがあれば、ビルドを止める。配布物は、配布フォルダのファイルを読まない。開発中(`python -m remi`)はファイルを読む
- 項目: `name`(名前。前回の実行時刻をこの名前で覚える)・`command`(プログラムと引数のリスト)・`interval_minutes`(間隔。5分未満は5分)・
  `run_at_startup`(起動したら、まず1回実行する。既定 false)・`timeout_seconds`(既定60、3600まで)。誤りのある項目は、記録して使わない
- `command` は、1つの要素が1つの引数になる。コマンドプロンプトを通さないので、`|` `>` `%VAR%` などは文字として渡る(使うときはバッチファイルにする)。
  プログラムの相対パスは Remi.exe のフォルダ(開発中はリポジトリの最上位)から探し、`../` で親のフォルダを指せる。作業フォルダも Remi.exe のフォルダ。
  引数の `{app_dir}`(Remi.exe のフォルダ)・`{version}`(Remi のバージョン)は、実行するときに置き換える(`{{` `}}` は `{` `}`)
- 前回の実行時刻はタスクごとに `settings`(`scheduled_task_last_run:<名前>`)に保存し、再起動しても引き継ぐ。実際の時計で比べるので、
  スリープ明けなどで過ぎていれば、すぐ実行する。初めてのタスクは、`run_at_startup` でなければ、そこから間隔を数え始める。
  実行の前に時刻を記録する(実行中に終了しても、次の起動ですぐ繰り返さない)
- 30秒ごとに時刻が来たかを確かめ、別のスレッドで1つずつ実行する。ウィンドウは出さず、時間内に終わらなければ止める。
  終了コード・見つからない・時間切れはログに残す。タスクの失敗で Remi は止めない
- Remi を終了するときは、実行中のコマンドも終了させ(Windows では、起動した先のプロセスも含めて止める)、スレッドが終わるのを待ってから、DBを閉じる
  (更新の取り込み中に、タスクがファイルを使い続けないように)。同期のスレッドが止まりきらないときは、DBの接続を閉じずに終える

## 9. 外観(ダークモード)

### 9.1 方針

- 設定項目 `theme`: **システムに従う(既定)/ ライト / ダーク**
- 「システムに従う」の場合は、CSSの `prefers-color-scheme` を使う。WebView2はWindowsのアプリの色設定に従うので、設定が変わると**再起動なしで即時に切り替わる**
- 「ライト / ダーク」を明示した場合は、`<html data-theme="light|dark">` で強制する
- ウィンドウのタイトルバーも、Windowsの `DwmSetWindowAttribute`(`DWMWA_USE_IMMERSIVE_DARK_MODE`)でダークに合わせる。
  この設定は、しばらく使わない・隠して出し直すなどで、Windows側で既定の色に戻ることがあるので、2秒ごとに付け直す
  (システムに従う設定のときは、システムの色の切り替えにも追従する)

### 9.2 色はセマンティックトークン(CSS変数)で管理する

色を直接書かず、`app.css` の `:root` に**意味ごとのCSS変数**をライト・ダークの2組で定義する。

| トークンの例 | 用途 |
| --- | --- |
| `--window` / `--surface` / `--surface-alt` | 背景、ペイン、一覧の背景 |
| `--text` / `--text-muted` / `--border` | 文字、補足の文字、枠線 |
| `--accent` / `--on-accent` | 強調色(未読バッジ、送信ボタン)、その上の文字 |
| `--bubble-other` / `--bubble-mine` / `--bubble-private` | 吹き出しの背景 |
| `--code-bg` / `--code-border` | コードブロック |
| `--link` / `--mention-bg` / `--danger` / `--success` / `--warning-bg` | リンク、メンション、エラー、成功、警告 |
| `--c-filter` / `--c-sort` / `--chip-mix` | 絞り込み(緑)・並べ替え(紫)の色と、条件のチップなどの背景に混ぜる割合(ライト16%・ダーク30%) |
| `--dot-ok` / `--dot-error` | ツリーのサーバーの状態の丸(接続中・接続できない)。両テーマで同じ色 |

- コードハイライトは、Pygmentsのクラス名付きHTMLにし、ライト用(`default`)とダーク用(`github-dark`)のCSSを切り替える
- ライトとダークのどちらでも、文字と背景のコントラスト比は4.5:1以上を確保する(テストで確認する)
- 色の違いで区別するもの(条件のチップの青・緑・紫など)は、両テーマで見分けられるようにする。
  暗い背景に薄く混ぜると、どの色も同じ暗い灰色に見えるので、ダークでは混ぜる割合を上げ(`--chip-mix`)、条件のチップには同じ系統の色の細い枠線も付ける
- 状態の丸は、文字用の `--success` / `--danger`(読めるよう、ライトは暗く・ダークは明るくしてある)を使わず、両テーマ共通の
  `--dot-ok` / `--dot-error` を使う(テーマで印象が変わらないように。どちらの背景でも3:1以上)
- 薄くする(不透明度を下げる)ことで状態を表さない(文字が読みにくくなる)。クローズ済みのステータスは、塗りなし・点線の枠で区別する
- 一覧の選択中の行は、背景(`--selection`)に加えて左に青い線を付ける(ライトでは、背景だけでは分かりにくい)
- 自分の吹き出しの中のメンションは、背景が吹き出しの色に溶けるので、細い枠線で区切る

### 9.3 トレイアイコン

Windowsでは、タスクバーの色(`SystemUsesLightTheme`)とアプリの色(`AppsUseLightTheme`)を別々に設定できる。アイコンは、どちらの背景でも見えるよう、青い角丸の背景に白い「R」と「e」を重ねた形で、色は共通にする(未読があるときは右上に赤い点を付ける)。タスクバー側の設定(`HKCU\Software\Microsoft\Windows\CurrentVersion\Themes\Personalize`)は読むが、アイコンの色の切り替えには使っていない。

## 10. 多言語対応

### 10.1 方針

- 翻訳は**キー方式のJSONカタログ**で管理する(`src/remi/i18n/en.json`、`ja.json`)。画面(JavaScript)とPython(通知、トレイメニュー、エラー)で同じカタログを使う
- 最初に対応する言語は**日本語と英語**。英語を基準にし、キーがそろっていることをテストで確認する
- 文言には `{name}` 形式の差し込みを使う。複数形が必要な文言は `Intl.PluralRules` の区分(`one` / `other`)ごとに持つ
- 設定項目 `language`: **システムに従う(既定)/ 日本語 / English**。画面は再読み込みだけで切り替わる
- 日付・数値の書式は、画面側で `Intl.DateTimeFormat` / `Intl.NumberFormat` を使い、選んだ言語に従う。「昨日」などの相対表現も翻訳対象にする

### 10.2 層ごとの扱い

| 層 | 扱い |
| --- | --- |
| 画面 | カタログのキーで文言を表示する |
| 同期エンジン・APIクライアント | **文字列ではなくエラーコードを返す**。画面またはPythonのUI部分(通知・トレイ)で翻訳する |
| ログ | 英語のみ(問い合わせのときに読みやすくするため) |
| Redmineから取得したデータ | ステータス名などはサーバーの言語のまま表示する |
| 変更履歴の項目名 | `status_id` などの属性名に対応する表示名は、アプリ側で翻訳する(カスタムフィールドはサーバーの名前を使う) |
| 変更履歴の値 | ステータス・担当者・優先度・トラッカー・プロジェクト・対象バージョン・カテゴリのIDは名前にする。カスタムフィールドは、形式(管理者だけが取得できる)が分かれば、ユーザー・バージョン・キー・バリューリストを名前に、真偽値を はい/いいえ にする。名前はチケット・バージョン一覧などに含まれていたものを覚えておき、知らないものはチケットを開いたとき(履歴の取得時)に `/versions/:id.json` などで問い合わせる(1回に20件まで。見えないもの・グループは #ID のまま) |

## 11. バージョン管理

- **セマンティックバージョニング 2.0.0**(`MAJOR.MINOR.PATCH`)に従う
- **ひとまずの完成までは、メジャーバージョンを `0` にする**。`0.y.z` の間は、機能追加でMINORを上げ、不具合修正でPATCHを上げる。破壊的な変更もMINORの更新で行ってよい
- バージョンの定義は `src/remi/__init__.py` の `__version__` の**1か所だけ**にする。`pyproject.toml` はそこから読む
- Pythonのパッケージ規約(PEP 440)とも矛盾しないように、バージョン文字列は `X.Y.Z` の形だけを使う(`-beta` などの付加ラベルは使わない)
- 変更履歴は `CHANGELOG.md`(Keep a Changelog形式)に書く。開発中の変更は `Unreleased` の節にためておき、リリースのときにバージョン番号の節へ移す
- Git のタグは付けない。どのバージョンかは、`__version__`(アプリの中)と、`CHANGELOG.md` のバージョンの見出しで決まる(`main` にマージした時点の内容が、そのバージョン)
- バージョン番号の表示先: ウィンドウのタイトル(`Remi vX.Y.Z`)、User-Agent(`Remi/X.Y.Z`)、exeのファイルバージョン(Windowsの4桁形式 `X.Y.Z.0`)
- DBのスキーマのバージョンは、アプリのバージョンとは別に `PRAGMA user_version` で管理し、起動時に順番にマイグレーションする。新しいスキーマのDBを古いアプリで開いた場合は、起動を中止してその旨を表示する
